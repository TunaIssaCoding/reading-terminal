# Reading Terminal — design

## Boundary and data model

The public site contains code, three explicitly fictional demo articles, and a browser-produced encrypted `vault.json` after setup. Private reading data is fetched directly from GitHub; no proxy, analytics, remote scripts, or server is involved. Normal vault credentials live in memory, optionally restored from an encrypted IndexedDB device record. `localStorage` stores theme, pane preferences, non-secret connection defaults, and a synchronous pending-write recovery journal. Only the explicit legacy manual-token connection persists a token in localStorage. IndexedDB stores a separate content cache and durable write queue for each owner/repository/branch; demo data uses its own namespace.

`library.json` is bot-owned metadata. `user/state.json` is a map keyed by article id; its status/star/timestamps override library fields. `user/notes/<slug>.json` contains long_notes, highlights and updated_at. Highlights carry id, quote, prefix, suffix, para, note, created_at and updated_at. Optional per-field timestamps and deleted-highlight tombstones preserve concurrent changes and deletions without changing the required schema. Bot summaries and metadata are read-only. A user edit containing note text promotes an item to commented; explicit status choices are allowed until the next note edit. Automatic read detection never demotes commented items.

Automatic Commented promotion stores the previous unread/read status in `commented_from`; deleting all note text restores it. Manual choices clear that provenance. Status and provenance merge as one conflict unit. Automatic status changes apply immediately with independent six-second Undo notices. Undo restores only status/provenance, preserving unrelated edits and note text; it refuses to overwrite a subsequent status decision. An undone automatic read is suppressed for the rest of that connection. Article opens do not enqueue writes: the first restore leaves state unchanged, and later `last_opened_at` values ride along with the next actual state edit.

## Module map and contracts

- `index.html`, `styles.css`: semantic three-column shell, dialogs, drawers, resize handle, dark/light themes. Desktop widths are 21vw / remaining / 30vw; the notes width can be resized.
- `js/app.js`: bootstrap, active article, settings/backup, status transitions, guarded keyboard routing, overflow/View controls, relative sync clock, shared six-second toast/Undo handling, body search and module integration. Each notice has its own timer; notices live in the active dialog's top layer when necessary. Highlight deletion/Undo is keyed to its original article, not whatever is currently open.
- `js/reader.js`: markdown source layout, persistent quote anchoring, selection toolbar, per-line interlinear editors and highlighted-passage drag payloads. `onDelete(highlight)` delegates immediate persistence and Undo to the app; selection actions reuse canonical offsets and quote data.
- `js/library.js`: `Library({root, onOpen, onStar, onStatus, onTag})`; `render(items, {activeId, query, tag, starredOnly, bodies, meta})`, `move(delta)`, `openFocused()`. Pure filtering/sorting, accordion state, safe DOM creation. `onOpen(id)`, `onStar(id)`, `onStatus(id,status)`, `onTag(tag)`.
- `js/notes.js`: `NotesPane({root, onChange, onOpen, notify})`; `setArticle(item, notes, botMarkdown)`, `updateMargins(highlights)`, `focus()`, `appendQuote(quote)`. Calls `onChange(longNotes)`; internal bot links call `onOpen(slugOrId)`. Owns the pane contents, not the pane shell/resize handle. Transient drop/append feedback uses the app's shared toast.
- `js/markdown.js`: `renderMarkdown(text)` returns escaped, safe HTML. No raw HTML execution; URL schemes are allowlisted. Supports headings, paragraphs, lists, block quotes, code, emphasis, links and images; internal article links stay local.
- `js/store.js`: `ReadingStore extends EventTarget`; `init() -> {library,state,meta}`, `getArticle(slug) -> string`, `getNotes(slug) -> object`, `getSummary(slug) -> string`, `getSearchIndex() -> {slug: text}`, `getAsset(path, from = '') -> blob URL`, `saveState(state)`, `saveNotes(slug,notes)`, `flush()`, `exportData()`, `importData(data)`, `testConnection()`. Constructor takes `{owner,repo,branch,token}`. `change` event detail `{status,message}` surfaces local/queued/sync/error states. Exported `mergeNotes(local,remote,base)` supports deterministic verification. `getSettings()` / `saveSettings(settings)` persist settings. `getNotes` returns independent values; save calls persist synchronously scheduled changes before network debounce. `init`/read operations use cached values during network failure and surface errors rather than inventing content. The optional search index falls back to lazy body reads without failing search.
- `js/demo.js`: exactly three fictional sample articles, sample user notes and bot summaries.
- `js/vault.js`: DOM-free WebCrypto envelope operations and validation. `createVault(payload,password)` returns `{vault,payload,dek}`; password/PRF unlock returns `{payload,dek}`. Immutable slot addition/removal and password replacement retain the DEK. Raw DEKs are 32-byte arrays kept only in memory or inside the encrypted remembered record.
- `js/passkey.js`: dynamic-hostname WebAuthn PRF registration, optional second assertion, credential-specific PRF evaluation, feature detection and default device labels.
- `js/session.js`: serialized `saveRemembered`, `loadRemembered`, and `deleteRemembered` operations. Separate `reading-terminal-session` database avoids changing the reading-cache schema.
- `js/vault-api.js`: cache-bypassing public vault fetch and restricted site-repository `vault.json` publication. Security commits three-way merge slots by id against the latest SHA, retry 409/422 once, preserve concurrent deletions, reject concurrent password replacements and never merge different vault identities/payloads.
- `js/auth.js`: boot/lock/setup routing, in-memory session ownership, Security UI and remembered-device lifecycle. The app receives credentials directly through `ReadingStore(settings)`, never through settings persistence.
- `sw.js`: network-first public app-shell cache with an offline fallback. GitHub API responses, vault.json, articles, notes and tokens never enter this service-worker cache. Vault requests, including direct navigations, bypass shell routing.
- Reconciliation events: `state-updated {state}`, `notes-updated {slug,notes}`, `article-updated {slug,markdown}`, and `summary-updated {slug,markdown}`. The app keeps newer event results when an article-opening request is still awaiting its other files. `dispose()` releases a replaced store's debounce, blob URLs and database handle.
- User article navigation pushes history; initial restoration replaces it. Both `popstate` and `hashchange` restore without pushing. Demo article hashes use `#demo&article=…`, preserving demo routing on reload without consulting a vault or token. Repo-root `assets/` paths and article-relative image paths use authenticated blob fetching; PDFs receive `application/pdf`. Items without body images get an `images[]` strip under the summary. The reusable `.bot-content` dashed box distinguishes intake summaries and existing bot-pane text from user notes; headings use supplied `summary_by`/`connections_by`, not a hard-coded writer. Compact density and theme are local-only controls under ⋯ → View; generated titles use subtle italics. Long notes resize on input, article load, quote append and width/font changes; the pane remains the scroll container.

## Select → highlight → note → drag state machine

Idle → a non-empty reader source selection stores a range and offers Highlight / Send to notes / Copy. `h` and the floating Highlight action share one operation. There is no contextmenu handler; right-click belongs to the browser. `selectionchange` supports touch selections; actual toolbar dimensions and `visualViewport` bounds keep it above the selection and inside the visible viewport, including zoom/scroll changes. Pointer-down on actions preserves selection. Selection spanning rendered text is converted to canonical paragraph/text offsets, quote and surrounding context. Exact quote and context choose an anchor on re-render; paragraph is a ranking hint, not an absolute dependency. Missing anchors are visibly reported and retained, never silently deleted.

Highlight creation → active interlinear note, keyboard focus immediately in the first gap. Source markdown is measured at the actual reader width and reconstructed as visual source lines using DOM Range fragments; images and block structure remain readable. Each source line has an explicit gap beneath it. The first note fragment starts at the highlight's first character, subsequent fragments use following line gaps. Text is wrapped by measured available width, not positioned in a floating card. Multiple notes share gaps by adding rows; after the source ends, extra gap rows are appended. Thus long or colliding notes expand local spacing and never cover source text. Editing a fragment updates the canonical note and reflows fragments while preserving logical caret position. Escape leaves editing; Backspace on an empty note closes it without deleting its highlight. A small delete button removes the highlight. Resize/font/image layout changes rebuild from canonical markdown and anchors, not from already fragmented DOM.

Soft markdown line breaks are normalized before measurement; mixed inline fonts use a line-height threshold rather than a font-dependent glyph top. Text surrounding inline images becomes separate source paragraphs, preserving both image display and text anchoring. `Reader.getHighlights()` supplies resolved reading-order offsets, including for older highlights without a stored `start`. Mobile drawers make closed panes and the covered reader inert to keyboard focus.

Highlighted text is draggable as `application/x-reading-highlight` plus `text/plain`, with a quote drag ghost. The notes pane accepts only an actual highlight drag, shows a drop target, and appends `\n\n> quote` after trimming trailing whitespace (one empty line). The same canonical notes object updates the reader and the read-only reading-order margin collection. Keyboard/touch users can also send a highlight to notes via its small action control.

## Sync and conflict handling

GitHub Contents API calls include a fine-grained bearer token and a configured branch. PUT is strictly restricted to `user/state.json` and safe `user/notes/*.json` paths. Reads cache content and SHA in IndexedDB; write queue entries include local content and the last known base content. Saves update the cache/queue before a two-second debounce; blur, hidden visibility and online events flush. Unsynced changes survive a reload. Requests are serialized per store to avoid stale SHA self-conflicts.

Before writing, fetch the current remote SHA. Three-way merge against the queued base: highlight ids use updated_at last-write-wins and tombstones; state uses field timestamps; unchanged sides do not conflict. Concurrent differing long-note edits preserve both with an explicit conflict marker, newer first. A 409/422 re-fetches and retries boundedly; authentication, rate limits, offline errors and exhausted conflicts leave the durable queue intact with an actionable status. Never PUT bot or article paths. A completed sync must not overwrite edits queued while a request was in flight.

Flush awaits outstanding user-file cache reconciliation before taking a write snapshot. This prevents a failed offline read from retaining a rejected repository-check promise into the first reconnect flush. An unavailable remote backup is explicitly marked `complete: false`, lists warnings, and downloads with `PARTIAL` in its filename; cached work remains exportable without falsely claiming a complete remote backup.

Settings order is Security, Backup, Connection, then the collapsed Advanced token disclosure. Settings include connection testing, explicit save/reconnect, export and import. Export contains all available user state/notes, not the token or private source articles. Import merges rather than discards existing notes and persists through the same queue. Relative private assets are fetched with authorization and cached as blobs, then exposed as object URLs; the token never appears in URLs. Demo mode exercises identical local editing and IndexedDB persistence without network requests. Successful private initialization/flush emits `synced`; the app records its local timestamp, renders relative age every 15 seconds, and keeps the exact time in `title`. Local demo, queued, syncing and failure states are not labelled as successful sync.

## UNLOCK security and lifecycle

### Public vault and offline guessing

`vault.json` is public, including its Git history. Its random 256-bit DEK encrypts the JSON connection payload with AES-256-GCM; payload AAD is the UTF-8 `vault_id`. Exactly one password slot wraps the same DEK using a non-extractable AES-256-GCM key derived with PBKDF2-SHA256, at least 600,000 iterations, and a fresh salt of at least 16 bytes. Lower iteration counts are refused. Each wrap binds `vault_id + ":" + slot.id` as AAD. IVs are independently random 12-byte values; ids and key material use `crypto.getRandomValues`.

The password only protects against offline guessing through its entropy and the PBKDF2 cost. The 12-character floor and strength hint are not a security guarantee: use **4–5 random words**, not a quotation or familiar phrase. Wrong passwords, malformed password envelopes and failed authentication share “That password did not unlock the library.” Setup clears both password fields after every attempt, but retains the GitHub token on validation/network/GitHub errors so it can be retried; success clears all three. Change password clears the current, new and confirmation fields on both success and error, including mismatches.

Each passkey slot uses its own 32-byte PRF salt. A 32-byte WebAuthn PRF result derives the wrapping key through HKDF-SHA256, using decoded vault-id bytes as salt and `reading-terminal-vault-v1` as info. The authenticator's private key and underlying PRF secret never leave the authenticator; its evaluated PRF result is necessarily returned to the browser for key derivation and is not persisted. RP id is the current hostname. User verification and resident credentials are required. A create-time PRF result is used directly; supported authenticators that omit it require a second prompt. Unsupported PRF commits no slot and leaves password unlock available.

Local WebAuthn checks use `http://localhost:<port>`, not `127.0.0.1`: the latter is not a valid WebAuthn RP id. `SecurityError` reports “Passkeys are not available on this address.” separately from unsupported PRF and prompt cancellation. The Chrome CDP smoke uses `ctap2_1`, `internal`, and `hasPrf: true` and requires registration, an encrypted vault commit, Lock and successful PRF unlock; an unsupported fallback is not a passing result. Physical authenticators remain a separate verification limit.

There is **no authentication server**. Challenges are random and assertion signatures are not verified against a server challenge. This is intentional: decryption depends on the secret PRF output, not on trusting an assertion signature or a client-side “authenticated” boolean.

### Device trust and revocation

Anyone possessing the unlocked GitHub token has **Contents read/write on both reading-data and reading-terminal**. Site code, the GitHub account, browser extensions and all scripts sharing the Pages origin must be trusted. Other projects on `tunaissacoding.github.io` share its origin/RP scope. XSS, malicious same-origin code, a compromised browser or an unlocked device can use or steal an unlocked token. CSP and safe markdown rendering reduce exposure but do not turn browser JavaScript into a hardware security boundary.

“Remember this device” stores a structured-cloned **non-extractable AES-GCM CryptoKey** in IndexedDB beside encrypted `{vault,payload,dek}`; vault identity and update timestamp are authenticated metadata. Non-extractable means WebCrypto cannot export the key: same-origin code can still use it to decrypt. Remembering is a convenience for a trusted browser profile, not another password or protection against a compromised profile. Turning it off deletes the device record and keeps credentials in memory only; no sessionStorage credentials are used.

Remembered sessions connect first, including offline. A background network-only vault check invalidates a different `vault_id`, deletes the record and locks the app, even if a security operation is still running. A delayed operation cannot restore a superseded session. Older same-identity Pages publications do not roll back a newer locally committed vault. Password/passkey commits update the in-memory vault and remembered metadata.

Lock gives sync up to 1.5 seconds, aborts remaining requests including response bodies, clears in-memory credentials/reader content, revokes store-owned blob URLs, and deletes the current library namespace's cached contents. **Unsynced edits and their merge bases remain in the durable queue and recovery journal**, and resume after the next unlock. Those edits, normal library caches before Lock, and downloaded backups are not encrypted by the vault. Clear browser data only after syncing/exporting if retiring a device; clearing it with queued edits loses those edits.

Removing a passkey or changing the password changes future unlocks against the current vault, not copies already saved by an attacker or Git history. Neither revokes a leaked token or an existing remembered session with the same vault identity. Passkey removal hides the row optimistically and waits for its six-second Undo notice to expire before publishing. Undo restores the row without a commit; pending removals cancel on Lock/session changes. Expired removals serialize behind other security operations; commit failures restore the row. For actual revocation, **delete/revoke the token on GitHub and run `#replace` with a new token and vault**. The separate replacement screen requires exact typed REPLACE; setup cannot overwrite an existing vault. Old passkeys stop working against the new vault. Background invalidation is eventual and requires seeing the new publication. An offline device cannot observe revocation until it reconnects.

### Setup and connection boundaries

A 404 public vault response opens setup (or the old manual-token connection when one exists); other load errors show Retry rather than treating failure as first use. The lock screen presents Password, Unlock, an available passkey button, Remember this device and Explore the demo; collapsed Other options contains setup and replacement links. Demo is explicit with a separate `demo:v1` namespace; loading `#demo` or a demo article hash opens that library before restoring a remembered session or fetching the vault. `#setup` never replaces; `#replace` has its own screen and exact REPLACE gate. The token only goes to `api.github.com` in Authorization headers; the password and plaintext DEK are never transmitted. Setup checks the private data repository, obtains the site file SHA and publishes encrypted JSON with message `Update reading vault`. A missing site file is distinguished from denied repository access.

Export/import continues to contain user state and notes only, never the token, DEK, vault or remembered-device key. Legacy manual-token settings remain under the last Advanced disclosure; a successful vault unlock removes any legacy stored token. Lock/setup/replacement screens isolate the background UI and bypass reading shortcuts. Inputs, textareas, all editable contenteditable forms and textbox-role editors bypass global reading shortcuts; the interlinear editor retains its local editing keys. Esc closes overlays/menus/drawers before returning from the reader to the library. Menus also close on outside pointer-down; Text-node event targets are normalized before element lookup.
